# Правила рантайма часов

Весь список выведен из дефектов, каждый из которых прошёл сборку, линтер, зелёные тесты и эмулятор, и проявился только на устройстве. Фактура — в [docs/vela-notes.md](../../../docs/vela-notes.md); здесь — то, что нужно проверять в коде.

## 1. Все исходы вызова ведут в одну функцию завершения

Модуль может сообщить результат через `success`, `fail`, `complete`, событийный слот (`onframerecorded`, `onDownloadComplete`) или не сообщить вовсе. Какие из них реально сработают — свойство прошивки, а не документации.

Поэтому: **ни один зарегистрированный колбэк не бывает пустым и не выбрасывает данные**.

```js
// Неверно: результат приехал сюда и потерялся, ждём другой путь.
success: function() {},
complete: settle(finish),

// Верно: любой исход резолвит, первый побеждает, данные не теряются.
success: function(data) { captured = data; settle(finish)(data) },
complete: settle(finish),
```

Стоимость ошибки на реальном примере: `startFramed` ждал только кадры и `complete`, а прошивка отдавала запись через `success({uri})`. Экран висел 18 секунд на сторожевом таймере, затем **молча включал микрофон второй раз**.

Порядок колбэков тоже не гарантирован: если `complete` может обогнать `success`, сохраняйте данные в переменную вне сторожа, чтобы поздний победитель их не потерял.

## 2. Сторожевой таймер — последний исход, а не единственный

`guard()` из `watch/src/common/guard.js` обязателен вокруг каждого системного вызова, но он страхует от молчания, а не заменяет колбэк. Признак, что правило нарушено: **операция всегда занимает ровно столько, сколько стоит таймаут**. Внешне это работающее приложение.

Проверка в ревью: для каждой ветки — какой колбэк её резолвит в штатном случае? Если ответ «сторож» — это дефект.

## 3. Объявленный метод ≠ работающий метод

`typeof mod.m === "function"`, `"m" in mod`, `hasOwnProperty` доказывают только объявление слота. В этом проекте уже дважды обожглись: `request.upload` существовал и молчал; `onframerecorded` объявлен и не заполняется.

Такая проверка — **предусловие**. Возможность считается подтверждённой только по наблюдаемому результату: пришёл кадр, вернулись байты, сработал колбэк.

И результат надо запоминать, иначе крюк оплачивается каждый раз:
- `rememberTransferMode` — в хранилище, переживает перезапуск;
- `framedUnsupported` в `audio.js` — переменная модуля, живёт сессию.

Выбор между ними — про радиус поражения: новый ключ хранилища требует правки `KEYS`, `copyDefaults`, `toStored`/`fromStored` **и** `saveSettings`. Один пропущенный пункт уже приводил к тому, что переключатель озвучки затирал серверный конфиг. Флаг модуля такой цены не имеет.

## 4. Функция возвращает либо `uri`, либо `bytes` — оба пути нужны всем потребителям

`@system.record` отдаёт путь к файлу; потоковый режим отдаёт байты в памяти. Добавляя второй вид результата, нужно пройти **всех** потребителей, а не только счастливый путь:

- отправку (`voiceUri` / `voiceBytes`);
- офлайн-очередь (`enqueueAudio`);
- диагностику;
- отмену и повтор.

Пропущенная очередь стоила потери надиктованной заметки: `enqueueAudio(undefined, …)` вызывал колбэк **успеха**, экран обещал «отправлю, когда появится сеть», а запись уже не существовала.

Отсюда правило API: **не сообщать об успехе, если сохранить нечего**. Нет данных — `fail`, и текст ошибки должен называть настоящую причину (место на часах), а не унаследованную (сеть).

## 5. Быстрый зелёный тест ничего не доказывает про зависание

Сторож делает тест зелёным — он просто дольше идёт. Поэтому для путей с фолбэком **утверждайте время**:

```js
const startedAt = Date.now()
const result = await new Promise((res, rej) => recordAudio(res, rej))
assert.ok(Date.now() - startedAt < 2000, `ждали ${Date.now() - startedAt} мс`)
assert.equal(starts, 1, "микрофон включается один раз")
```

И считайте побочные эффекты: сколько раз вызван `record.start`, сколько запросов ушло, сколько элементов в очереди. Дефект «молча записал второй раз» виден только по счётчику.

Тестовые двойники в `watch/testkit/system.mjs` должны уметь изображать **вредную** прошивку, а не только дружелюбную: слот объявлен, но событий нет; `success` без `complete`; `complete` раньше `success`; метода нет вовсе.

## 6. Что проверять перед тем, как называть правку готовой

- Каждый системный вызов: обёрнут сторожем **и** имеет штатный резолвер, не совпадающий со сторожем.
- Каждый колбэк: либо использует свои данные, либо явно объяснено, почему нет.
- Новый вид результата: пройдены отправка, очередь, диагностика, отмена.
- Новый ключ настроек: добавлен в `KEYS`, `copyDefaults`, `toStored`, `fromStored` и сохраняется в `saveSettings` (тот засевается из `cached`, не из дефолтов).
- Новая ветка фолбэка: есть тест на время и на число побочных вызовов.
- Новое состояние захвата: попало в `capture.mode` и в [docs/physical-checklist.md](../../../docs/physical-checklist.md) с расшифровкой — иначе отчёт с устройства нечем читать.

## 7. Чего локальная проверка не закрывает в принципе

Микрофон, динамик и Tuya подтверждаются только на устройстве. Эмулятор даёт нулевую запись, `sendMouse` не работает, мелкие цели в сетку касаний не попадают. Отчёт диагностики уходит в `console.log` шлюза, то есть в рантайм-логи хостинга (строка `DIAG`), и **нигде не сохраняется** — забирать оттуда.

Поэтому в коде для часов дешевле заранее заложить видимый фолбэк, чем надеяться на проверку: зависший экран на руке не диагностируется, а неверный путь, о котором приложение честно сообщило, — диагностируется.
