# Публикация сборки часов

## Главное ограничение

Репозиторий **публичный**, а собранный RPK содержит адрес шлюза и токен устройства **открытым текстом**. Проверяется за минуту: распаковать `.rpk` как zip и найти строку токена в `pages/index/index.js`.

Так устроено не по небрежности: на часах нет ввода текста (`prompt.show` в рантайме отсутствует, элемента `input` нет), поэтому адрес и токен задаются на этапе сборки из `watch/src/common/config.local.js`. Настроить приложение на устройстве нечем.

Токен на шлюзе один и плоский: он открывает вопросы к модели, заметки и управление светом через Tuya. Публикация сборки = публикация всего этого.

**Отсюда правило: собранный `.rpk` не прикладывается ни к коммиту, ни к релизу, ни к issue, ни к сообщению — никогда, пока у шлюза нет отдельного токена с урезанными правами.** Файл можно отдать человеку напрямую в этой сессии (`SendUserFile`) — это не публикация; выложить в репозиторий нельзя.

## Что делать при каждом пуше, меняющем `watch/`

1. Прогнать проверку:

   ```bash
   cd watch && npm run release:check
   ```

   Она падает, если токен из `config.local.js` нашёлся в любом файле под контролем версий. Та же проверка продублирована в `watch/test/release-safety.test.mjs`, поэтому её нельзя обойти забывчивостью.

2. Обновить [docs/release.md](../../../docs/release.md): `versionCode`, размер и раздел «Что в этой версии». Это и есть страница последней версии — она описывает то, что лежит в `main`.

3. Версию **не править руками**: `prebuild` поднимает `versionCode` сам. Из-за этого номер иногда перескакивает — проверочная сборка тоже считается. Это нормально, достаточно упомянуть в сообщении коммита.

4. Бамп `manifest.json` коммитить отдельным коммитом `TimeW vNN: <что упаковано>`, как в истории.

## Чего не делать

- Не выкладывать `.rpk` в релизы GitHub и не коммитить `watch/dist/`.
- Не собирать CI-сборку «для всех»: токен-нейтральный RPK бесполезен (покажет «Шлюз не настроен» и настроить его будет нечем), а RPK с токеном публиковать нельзя.
- Не вписывать токен или адрес шлюза в документацию, тесты и сообщения коммитов. Адрес сам по себе не секрет, но пара «адрес + токен» — секрет целиком.
- Не печатать токен в вывод скриптов и тестов. `release-check` сообщает только длину.

## Если попросят публичную тестовую сборку

Сказать прямо, что сейчас это небезопасно, и назвать условие: шлюзу нужен **второй токен с урезанными правами** — без `/api/v1/home/*`, со своим низким лимитом запросов, желательно без доступа к заметкам. Модель прав сейчас плоская (`config.token`, одна проверка в `authorized()`), так что это отдельная работа, а не настройка.

Порядок, если её решат делать: сначала область действия токена на шлюзе и тесты на то, что демо-токен получает `403` на домашних ручках, потом уже сборка.

## Если токен всё-таки утёк

Смена дешёвая, сделать сразу:

```bash
cd server && npm run setup
```

Скрипт перевыпустит `DEVICE_TOKEN` в `server/.env` и перезапишет `config.local.js`. После этого передеплоить шлюз и пересобрать часы — старая сборка перестанет подходить. Удаления файла из истории git это не отменяет: если токен попал в коммит, его надо считать скомпрометированным независимо от того, удалён ли файл потом.
