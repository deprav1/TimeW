# Протокол TimeW v0.2

Все запросы идут по HTTPS. Часы передают заголовок `X-TimeW-Device-Token`, если на шлюзе задан `DEVICE_TOKEN`.

Исключение — `GET /health`: он публичный и работает без токена, чтобы можно было проверить доступность шлюза до настройки часов.

## Формат ошибок

Любая ошибка возвращается одинаково:

```json
{"ok":false,"error":{"code":"bad_request","message":"text is required"}}
```

| HTTP | `code` | Когда |
| --- | --- | --- |
| 400 | `bad_request` | пустой `text`, невалидный JSON, некорректный `limit`, пустое или битое аудио |
| 429 | `rate_limited` | превышен `RATE_LIMIT_MAX` запросов за `RATE_LIMIT_WINDOW_MS` |
| 401 | `unauthorized` | задан `DEVICE_TOKEN`, а заголовок отсутствует или не совпал |
| 404 | `not_found` | неизвестный путь или удаление несуществующей заметки |
| 413 | `request_error` | тело больше лимита (`MAX_AUDIO_BYTES` для аудио, 64 KiB для JSON) |
| 502 | `provider_error` | AI-провайдер вернул ошибку или недоступен |
| 503 | `provider_error` | лимит AI исчерпан (провайдер ответил 429) |
| 504 | `provider_error` | провайдер не ответил за `AI_TIMEOUT_MS` (по умолчанию 20 с) |
| 500 | `internal_error` | всё остальное; подробности только в логе шлюза |

Сравнение токена выполняется по константному времени, поэтому подбор по задержке ответа не работает.

## CORS

`OPTIONS` на любой путь отвечает `204` без тела и с заголовками:

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET, POST, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, X-TimeW-Device-Token, Idempotency-Key, X-TimeW-Request-Id
Access-Control-Max-Age: 86400
```

## Health

`GET /health` — без токена.

```json
{"ok":true,"service":"timew-gateway","mode":"demo","version":"0.2.0","buildId":"local"}
```

`mode` — `demo`, когда `AI_PROVIDER=mock` или не задан ключ, иначе `live`.

`GET /api/v1/status` — защищённый статус для часов (требует токен). Возвращает
эффективный режим и флаги возможностей без ключей и других секретов:

```json
{"ok":true,"service":"timew-gateway","mode":"demo","provider":"mock","buildId":"local","configRevision":"voice-1","runtime":{"revision":"voice-1","maxRecordingMs":10000,"silenceThreshold":450,"silenceDurationMs":1000,"speechGraceMs":900,"frameSize":2048,"requestTimeoutMs":35000,"uploadTimeoutMs":60000,"ttsFormat":"mp3","autoStop":false,"capabilities":{"frameRecording":"probe","immediateLight":false,"undoLight":false}},"capabilities":{"ai":false,"notes":true,"speech":false,"home":false,"homeConfirmation":false,"immediateLight":false,"undoLight":false,"autoStop":false}}
```

`runtime.autoStop` — разрешение часам использовать потоковый режим записи с
автостопом по паузе. **По умолчанию `false`**: в этом режиме `@system.record`
не отдаёт файл (документированное поведение при заданном `frameSize`), поэтому
вся запись держится в памяти часов. Включается явным `AUTO_STOP_ENABLED=1` и
только на прошивке, где это проверено на устройстве. Часы трактуют любое
значение кроме `true` как выключено.

## Текстовый запрос

`POST /api/v1/query`

```json
{"text":"Какая погода завтра?"}
```

Шлюз сам определяет намерение и возвращает одно из трёх значений `kind`.
Для защиты от повторной доставки часов можно передать `Idempotency-Key` (или
`X-TimeW-Request-Id`, либо `requestId` в JSON). В течение 10 минут повтор того
же запроса возвращает исходный ответ и не создаёт дубль заметки; повтор с тем
же ключом для другого тела даёт `409 idempotency_conflict`.

**`kind: "ai"`** — обычный вопрос уходит провайдеру:

```json
{"ok":true,"kind":"ai","text":"...","source":"demo"}
```

**`kind: "note"`** — текст начинается с «запиши», «заметка», «запомни» или `note`:

```json
{"text":"Запиши: купить фильтр"}
```

```json
{
  "ok": true,
  "kind": "note",
  "text": "Записал: купить фильтр",
  "note": {"id":"ddd3d71a-…","text":"купить фильтр","createdAt":"2026-09-17T15:42:03.398Z"},
  "source": "local"
}
```

**`kind: "home"`** — распознана команда умного дома. Для точной команды
включения/выключения света в одной настроенной комнате шлюз сразу вызывает
Tuya и возвращает квитанцию. Действие можно один раз отменить в течение 30
секунд через `undoToken`:

```json
{"ok":true,"kind":"home","command":{"action":"off","device":"light","room":"bedroom"},"executed":true,"requiresConfirmation":false,"text":"Выключил свет в спальне","devices":["…"],"undoToken":"…","undoExpiresAt":"…","undoAvailable":true,"source":"tuya"}
```

`POST /api/v1/home/undo` с телом `{"undoToken":"…"}` выполняет обратное
действие. Повторный или истёкший токен даёт `410 undo_expired`. Розетки,
замки, ворота и сигнализация остаются заблокированными; неоднозначная комната
или отсутствие карты устройств никогда не приводит к вызову Tuya.

Для заблокированных категорий ответ содержит `requiresConfirmation:true`, но не
содержит токена: подтверждение с часов намеренно не запускается, а команда
остаётся только сообщением «нужна проверка на телефоне». Поле и endpoint
`/api/v1/home/confirm` зарезервированы для будущего безопасного телефонного
сценария и сейчас не являются рабочим путём управления.

Если комната не распознана, `room` будет `null`, а `text` попросит уточнить. Это сознательная граница первой беты: Google Home SDK и OAuth появятся в Android-компаньоне после проверки видимости конкретных Tuya-светильников.

Текст запроса нормализуется и обрезается до 500 символов. Тело JSON ограничено 64 KiB.

## Голосовой запрос

`POST /api/v1/voice` — **основной путь для часов**: аудио на входе, готовый ответ на выходе.

Принимает аудио в тех же двух форматах, что и `/api/v1/transcribe` (см. ниже). Возвращает и расшифровку, и результат:

```json
{"ok":true,"transcript":"Сколько лететь до Лиссабона","kind":"ai","text":"...","source":"gemini","speechId":"…"}
```

kind определяется так же, как в /api/v1/query: при intent=note и preview=1 шлюз только распознаёт текст и возвращает kind=draft; заметка сохраняется только отдельным подтверждённым запросом. Точная команда света выполняется сразу; обычный вопрос уходит модели.

Успешный голосовой ответ дополнительно содержит `requestId` и безопасные
`timings` (`recordMs`, `receiveMs`, `providerMs`, `tuyaMs`, `totalMs`). Шлюз
пишет эти же этапы одной строкой в лог, без текста, аудио и ключей.

Зачем отдельный эндпоинт: раньше часы делали два круга — сначала расшифровка, потом вопрос. На часах Wi-Fi поднимается по требованию, поэтому лишний круг стоит секунд. Для Gemini шлюз делает **один** вызов, в котором модель и расшифровывает, и отвечает.

Важная граница: если расшифровка оказалась заметкой или домашней командой, ответ модели **отбрасывается** и работает собственный разбор шлюза. Экономия круга не даёт модели влиять на то, что исполняется.

## Выбор модели

`/api/v1/query` и `/api/v1/voice` принимают провайдера — в теле (`"provider": "gemini"`) или в query-строке (`?provider=gemini`).

Допустимо: `auto` или отсутствие поля (использовать настройку шлюза), `gemini`, `openai`. Иное значение — 400. Провайдер без ключа на шлюзе — 503, а не молчаливый откат в demo-режим.

## Память диалога

Шлюз помнит последние `DIALOG_TURNS` обменов (по умолчанию 6) не дольше `DIALOG_TTL_MS` (по умолчанию 15 минут), чтобы работали уточнения вроде «а подробнее?». В историю попадают только обмены с `kind:"ai"` — заметки и домашние команды не часть беседы.

`POST /api/v1/dialog/reset` очищает историю:

```json
{"ok":true,"cleared":4}
```

## Озвучка

В Vela нет модуля синтеза речи, а `@system.audio` проигрывает только ссылку — он не принимает байты и не умеет POST с заголовками. Поэтому:

1. ответ с `kind:"ai"` содержит короткоживущий `speechId` (живёт `SPEECH_TTL_MS`, по умолчанию 5 минут);
2. часы скачивают аудио через `GET /api/v1/speak/:id` с токеном в заголовке (`request.download` заголовки поддерживает) и проигрывают локальный файл.

Синтез **ленивый**: при выдаче `speechId` ничего не синтезируется. Реальный вызов провайдера происходит только при запросе аудио — иначе шлюз платил бы за озвучку каждого ответа, включая те, что никто не слушает (по умолчанию озвучка на часах выключена).

Неизвестный или протухший идентификатор — 404. Синтез не настроен — 503.

Для проверки с компьютера есть `POST /api/v1/speak` с телом `{"text":"…"}` (до 1000 символов), отдающий аудио напрямую. Формат — `audio/mpeg` или `audio/wav` согласно эффективной настройке шлюза; для OpenAI-совместимого провайдера можно безопасно указать разовый `?format=mp3|wav`. Gemini всегда возвращает WAV.

При `AI_PROVIDER=gemini` TTS по умолчанию использует тот же `AI_API_KEY` и
Gemini speech model; отдельный ключ не нужен. `TTS_PROVIDER=openai-compatible`,
`TTS_API_KEY` и `TTS_BASE_URL` нужны только для отдельного OpenAI-совместимого
синтеза. Ключ Gemini никогда не передаётся в такой endpoint.

## Заметки

`GET /api/v1/notes?limit=N`

`limit` — целое от 1 до 50, по умолчанию 5. Значения больше 50 зажимаются, некорректные дают 400. Заметки отсортированы от новых к старым; на диске хранятся последние 50.

```json
{"ok":true,"notes":[{"id":"ddd3d71a-…","text":"купить фильтр","createdAt":"2026-09-17T15:42:03.398Z"}]}
```

`DELETE /api/v1/notes/:id`

```json
{"ok":true,"deleted":true,"id":"ddd3d71a-…"}
```

Несуществующий `id` → 404 `not_found`.

Все операции с заметками сериализованы в очередь, поэтому параллельные запросы не затирают друг друга.

## Аудио

`POST /api/v1/transcribe` принимает запись в **двух форматах** — это не избыточность, а следствие того, как устроена запись на часах.

`@system.record` на Watch S5 возвращает не байты, а `uri` файла в кэше приложения. Документация Xiaomi не описывает, как такой файл доставить на сервер, поэтому часы пробуют два способа подряд, и шлюз понимает оба.

**Сырое тело** — `Content-Type: audio/opus`, `audio/wav` или `application/octet-stream`, в теле сами байты. Так отправляет запасной путь часов (`file.readArrayBuffer` + `fetch`).

**multipart/form-data** — `Content-Type: multipart/form-data; boundary=…`. Так отправляет основной путь часов (`request.upload`). Шлюз берёт первую часть, у которой в `Content-Disposition` есть `filename` (имя поля не важно). Тип аудио определяется по `Content-Type` этой части, а при его отсутствии — по расширению файла (`.opus`, `.wav`, `.pcm`). Если файловой части нет, `boundary` отсутствует или тело битое — 400, а не 500.

Ограничение `MAX_AUDIO_BYTES` (по умолчанию 1 MiB) действует в обоих случаях, превышение даёт 413. Пустое тело — 400.

Ответ одинаковый:

```json
{"ok":true,"text":"...","source":"demo"}
```

В реальном режиме шлюз отправляет байты в OpenAI-совместимый `/audio/transcriptions` либо в Gemini `generateContent` с `inlineData`, в зависимости от `AI_PROVIDER`.

## Проверка протокола

Юнит- и HTTP-тесты: `npm test` в `server/` (80 тестов, сеть не используется).

Дымовой прогон против запущенного шлюза:

```bash
node scripts/smoke.mjs http://127.0.0.1:8787
```

С токеном — `TOKEN=... node scripts/smoke.mjs …`; с `--audio` дополнительно проверяется реальное распознавание (тратит запрос к провайдеру).
