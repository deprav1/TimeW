# Официальные правила Vela и наше соответствие им

В отличие от [vela-notes.md](vela-notes.md), где собран опыт с эмулятора и устройства, здесь — то, что Xiaomi написала сама, со ссылками, и колонка «как у нас». Проверено 19 сентября 2026 года.

Источники: [Memory Optimization](https://iot.mi.com/vela/quickapp/en/guide/best-practice/memory.html), [Common Business Optimization](https://iot.mi.com/vela/quickapp/en/guide/best-practice/business.html), [Startup Latency Optimization](https://iot.mi.com/vela/quickapp/en/guide/best-practice/start.html), [Acceptance Criteria](https://iot.mi.com/vela/quickapp/en/guide/publish/acceptance-criteria.html), [Precautions](https://iot.mi.com/vela/quickapp/en/guide/other/tips.html).

## Приёмочный критерий

Один и формальный: **First Meaningful Paint главного экрана ≤ 2000 мс**. Всё остальное ниже — рекомендации, но именно из них складывается это число.

У нас первый экран ждёт `loadSettings`. Чтение ключей идёт параллельно с потолком в 1 секунду на весь набор (`STORAGE_TIMEOUT_MS` в `settings.js`), а не по ключу — до этого молчащее хранилище стоило бы восьми секунд и одного проваленного критерия.

## Память

| Правило | Как у нас |
| --- | --- |
| Гасить незавершённые таймеры в `onDestroy` | ✅ после аудита: `index.ux` гасит `setInterval` счётчика и `setTimeout` отмены. Таймеры на `diag`/`settings` одноразовые и живут внутри `guard` |
| Не держать в `private`/`protected` данные, не привязанные к UI | ⚠️ на главном экране 9 из 21 поля не встречаются в шаблоне (`voiceEpoch`, `tickerId`, `settingsReady`, `lastSyncAt`, `undoTimer`, `recording`, `busy`, `answerSource`, `speechId`) — лишние наблюдатели. Не трогаем на горячей странице без нужды, но новые поля так заводить не надо |
| Обновлять объекты на месте, а не переприсваивать | ✅ соблюдается |
| Не кэшировать свойства страницы в глобальную область | ✅ не делаем |
| Освобождать прочитанные данные файла/хранилища сразу после использования | ✅ `pcmFramesToWav` отпускает кадры до вычисления base64 |
| `global.runGC()` — точечно, не часто | не используем; кандидат после отправки крупной записи |
| Атрибут `static` для неизменяемых привязок | ⚠️ не используется нигде. Кандидаты: заголовки экранов, подписи кнопок |
| Меньше страниц | ✅ пять: index, notes, answer, settings, diag |
| Лёгкие зависимости | ✅ рантайм-зависимостей нет вообще |

## Списки и рендеринг

| Правило | Как у нас |
| --- | --- |
| Список длиннее 10 элементов — пагинация | ✅ шлюз отдаёт по умолчанию 5 заметок (`parseNotesLimit`), потолок 50 |
| В `list-item` осторожно с `if`/`show`: структура элементов должна совпадать | ✅ в списках условных веток нет |
| Меньше вложенности тегов, меньше динамических стилей | ✅ верстка плоская; класс биндится целиком (иначе составные селекторы не работают, см. vela-notes) |
| `border-radius` поверх картинок заменять картинками со скруглением | не применимо: фоновых изображений нет |

## Сеть и жизненный цикл

| Правило | Как у нас |
| --- | --- |
| **`onShow` срабатывает заново при каждом включении экрана — осторожно с запросами в нём** | ✅ после аудита: `fetchStatus` убран под то же 30-секундное окно. До этого каждое пробуждение экрана било в шлюз |
| Меньше запросов и меньше одновременных | ✅ голос — один запрос вместо двух (`/api/v1/voice`) |
| Кэшировать то, что не требует свежести | ✅ настройки рантайма, заметки, очередь |
| Защищаться от повторных нажатий на кнопки, шлющие запросы | ✅ флаг `busy` + `voiceEpoch` |
| Индикатор ожидания на долгих запросах | ✅ бегущий счётчик |
| Не хранить сырой ответ сети в памяти, только нужные поля | ✅ |
| Обработка отсутствия сети, ошибок бэкенда и исключений JS | ✅ отдельные сообщения, `try/catch` вокруг системных вызовов |

## Старт

| Правило | Как у нас |
| --- | --- |
| Не задерживать переход `setTimeout`, ждать асинхронный результат напрямую | ✅ переходов с заставки нет |
| Не делать HTTP на стартовом экране | ⚠️ заставки нет, главный экран сам по себе стартовый; запрос статуса теперь под ограничителем, но он всё же на первом экране. При слабой сети это не блокирует отрисовку — колбэк ничего не ждёт |
| Минимум логов в консоль, особенно длинных и с JSON | ✅ на часах в рантайм не пишем (`console.log` всё равно не доходит до logcat) |
| Кэш данных главного экрана между входами | ✅ `notes-cache`, `runtimeConfig` |

## Что документация закрывает, а мы проверить не можем

Приёмочный критерий FMP измеряется инструментами AIoT-IDE на устройстве. Локально он не проверяется, поэтому в [physical-checklist.md](physical-checklist.md) стоит смотреть на время до первого экрана глазами: если между запуском и появлением кнопки «Говорить» заметная пауза — правило нарушено.
