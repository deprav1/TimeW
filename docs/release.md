# Последняя версия

Страница обновляется при каждом пуше, меняющем приложение часов. Здесь всегда описана та сборка, которая лежит в `main`.

| | |
| --- | --- |
| `versionCode` | **56** |
| `versionName` | 0.3.0 |
| Устройство | Xiaomi Watch S5 (`minPlatformVersion` 1000) |
| Размер RPK | ~90 КБ |
| Собирается | `npm run build` в `watch/` |

## Что в этой версии

- Кнопка «Заметка» на главном экране сразу начинает диктовку, а не просто открывает список.
- Диагностика проверяет динамик по-настоящему: качает с шлюза фиксированную фразу и проигрывает её.
- В отчёт попали причины отказов записи, результат проверки звука и этапы последнего голосового запроса.

- Запись работает файловым путём Opus; автостоп по паузе выключен по умолчанию и включается только `AUTO_STOP_ENABLED=1` (см. [protocol.md](protocol.md)).
- Озвучка сообщает причину молчания: при нулевой громкости мультимедиа пишет «Звук на часах выключен» вместо тишины.
- Ответ читается крупно: 28px на экране полного ответа, 27px на главном, кнопка «Говорить» — 400×116 с подписью 30px.
- Диагностика докладывает громкость, состояние последнего воспроизведения и режим захвата; последние пять отчётов забираются с `GET /api/v1/diag`.
- **Звук заработал, и заработал быстро.** Отчёт с часов показал, что `request.download` отвечает кодом 1000 сколько его ни опрашивай (тринадцать и четырнадцать попыток в двух прогонах), поэтому озвучка теперь сразу едет текстом: шлюз отдаёт её строкой base64 (`?as=base64&rate=8000`), часы пишут файл через `file.writeArrayBuffer` и играют оттуда. Пятнадцать секунд ожидания мёртвого пути ушли из каждой озвучки. Файловая загрузка включается обратно переменной `SPEECH_TRANSPORT=download`.
- **После ответа снова можно говорить.** Микрофон и динамик на этой прошивке не уживаются: естественный конец файла не отпускает аудиосессию, и `record.start` отвечал кодом 202 — тем же, что и на неверные параметры. Снаружи это выглядело как «первый ответ услышал, дальше ничего не работает». Теперь сессия освобождается явно, а запись ждёт четверть секунды после остановки озвучки; пауза отменяется вместе с записью.
- **Озвучка ответов включена по умолчанию.** Выключенная озвучка неотличима от сломанной, а часы — это прежде всего голос.
- Озвучка дожидается файла. `request.download.header` уходит документированной строкой — с ней рантайм перестал отклонять сам вызов (был отказ 202, «неверные параметры»), и отказ сместился на шаг дальше: `onDownloadComplete` отвечал кодом 1000, потому что его спрашивали один раз, пока шлюз ещё синтезировал фразу — а это около трёх секунд. Теперь опрос повторяется раз в 700 мс не дольше 15 секунд, число попыток уходит в отчёт; код 1001 («задачи нет») не повторяется.
- `@system.uploadtask` добавлен в runtime-зонд, но ещё не выбран рабочим транспортом без физического подтверждения.
- Запись при отказе параметров проходит через три ступени: полный Opus → минимальный Opus → `duration`-only.
- Все пять экранов собраны заново под круглый экран и сняты в эмуляторе по одному. Что изменилось и почему:
  - страница занимает все 480px (при 360px рантайм прижимал содержимое влево, и левый край уходил под рамку), раскладка идёт трапецией: ряды кнопок по 276px сверху и снизу, блоки до 400px в середине;
  - заливка только сплошным цветом — `linear-gradient` рантайм не рисует вовсе, и главная кнопка «Говорить» была невидимой, а `box-shadow` вокруг неё превращался на часах в широкое кольцо посреди экрана;
  - `list` и `list-item` не рендерятся ни в каком виде: экран полного ответа был пустым, а строки диагностики и заметки не появлялись. Всё переведено на `scroll` + обычные `div`;
  - `scroll` не обрезает содержимое, а прокрутку проверить нечем, поэтому длинное листается явно: ответ — страницами по тапу, заметки — по две кнопкой «Ещё», диагностика показывает последние шесть строк;
  - мелких подписей-ссылок не осталось: «заметки» и «настр.» стали кнопками, «начать заново» переехало в настройки, минимальная цель — 68px.
- Таймеры гасятся при разрушении страницы, запрос статуса не уходит при каждом включении экрана.
- Отчёт о воспроизведении сбрасывается в начале каждой попытки: диагностика показывает текущую озвучку, а не предыдущую.

## Почему здесь нет готового `.rpk`

**Собранный RPK содержит токен устройства открытым текстом.** Это проверяемо: распакуйте архив как обычный zip и найдите строку токена в `pages/index/index.js`. Токен попадает туда из `watch/src/common/config.local.js` на этапе сборки — так устроена конфигурация, потому что на часах нет ввода текста и задать адрес со шлюзом руками негде (подробности в [vela-notes.md](vela-notes.md), раздел про отсутствие `prompt.show`).

Репозиторий публичный. Выложить сюда собранный RPK — значит опубликовать токен, а токен на шлюзе один и открывает всё: расход AI-ключа, заметки и управление светом через Tuya. Поэтому в релизах лежит только исходный код, а бинарник каждый собирает под свой шлюз.

Токен-нейтральная сборка (`config.local.js` пустой) технически возможна, но бесполезна: приложение покажет «Шлюз не настроен», а исправить это на устройстве нечем — ввода текста в рантайме нет. Настройка существует только на этапе сборки.

## Как собрать свою версию

Нужны Node.js 20+ и один раз — интернет для зависимостей.

**1. Настроить шлюз.** В `server/` создайте `.env` по образцу `.env.example` и выполните:

```bash
cd server && npm run setup
```

Скрипт сгенерирует `DEVICE_TOKEN`, запишет его в `server/.env` и создаст `watch/src/common/config.local.js` с адресом шлюза и тем же токеном. Оба файла в `.gitignore` и в репозиторий не попадают.

**2. Собрать приложение часов.**

```bash
cd watch && npm install && npm run build
```

`prebuild` сам поднимет `versionCode` — вручную его править не надо. Готовый файл: `watch/dist/com.timew.personal.debug.0.3.0.rpk`.

**3. Установить.** Mi Fitness → Я → О программе → Отладка → Установить стороннее приложение.

**4. Проверить.** Порядок проверки на живом устройстве — в [physical-checklist.md](physical-checklist.md).

## Жёсткие лимиты

Все значения — умолчания; меняются через env шлюза без пересборки часов.

| Лимит | Значение | Переменная |
| --- | --- | --- |
| Запросов с одного адреса | 120 за 60 с, дальше `429` | `RATE_LIMIT_MAX`, `RATE_LIMIT_WINDOW_MS` |
| Размер аудио | 1 МиБ, дальше `413` | `MAX_AUDIO_BYTES` |
| Размер JSON-тела | 64 КиБ, дальше `413` | — |
| Текст запроса | 500 символов, обрезается | — |
| Текст на озвучку | 1000 символов, дальше `400` | — |
| Длительность записи | 10 с | `RECORDING_MAX_MS` |
| Ответ провайдера | 20 с, дальше `504` | `AI_TIMEOUT_MS` |
| Память диалога | 6 пар реплик, 15 минут | `DIALOG_TURNS`, `DIALOG_TTL_MS` |
| Жизнь `speechId` | 5 минут | `SPEECH_TTL_MS` |
| Заметок в выдаче | 5 по умолчанию, максимум 50 | параметр `limit` |
| Отмена действия с домом | 30 с, один раз | — |
| Идемпотентность | 10 минут, 200 записей | — |

Отдельно: у AI-провайдера свои квоты, и шлюз их не обходит. Исчерпанный лимит провайдера приходит как `503`.

## Если нужна публичная тестовая сборка

Тогда токен в ней будет публичным по определению, и раздавать текущий нельзя — он даёт полный доступ к шлюзу. Безопасный вариант требует доработки шлюза: **отдельный токен с урезанными правами** — без управления домом, с собственным низким лимитом запросов и, вероятно, без доступа к заметкам. Сейчас модель прав плоская: один `DEVICE_TOKEN` открывает все ручки. Пока такого разделения нет, публичной сборки с ключом быть не должно.

## Правило публикации

Перед каждым пушем, меняющим `watch/`, прогоняется проверка:

```bash
cd watch && npm run release:check
```

Она падает, если токен из `config.local.js` нашёлся хоть в одном файле под контролем версий, и отдельно сообщает, персональная сейчас сборка в `dist/` или нейтральная. Та же проверка живёт в тестах (`watch/test/release-safety.test.mjs`), так что забыть её нельзя.
