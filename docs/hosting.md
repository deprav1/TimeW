# Шлюз на бесплатном хосте

Пока шлюз живёт на домашнем компьютере, часы работают только когда компьютер
включён и не спит. Этот документ — про то, как убрать эту зависимость
бесплатно.

## Почему Deno Deploy

Перебирали то, что бесплатно и всегда включено:

| Куда | Правки кода | Что мешает |
| --- | --- | --- |
| **Deno Deploy** | хранилище | — |
| Vercel | хранилище | нужен отдельный сервис под базу |
| Cloudflare Workers | больше всего | другая модель запуска целиком |
| Render (бесплатный) | нет | засыпает, холодный старт под минуту |
| Oracle Always Free | нет | регистрация проходит не у всех |
| VPS | нет | ~$3 в месяц |

Deno Deploy выбран за три вещи: не нужна карта, KV встроен (не нужен второй
сервис под базу) и нет засыпания — для часов это важнее всего, потому что
холодный старт под минуту означает «приложение не работает».

## Что пришлось изменить в шлюзе

На бесплатных хостах между запросами не остаётся ни диска, ни памяти
процесса: каждый запрос может прийти в новый экземпляр. Шлюз опирался на
оба, и молча ломалось бы ровно то, от чего зависит корректность:

- заметки просто исчезали бы;
- ключи идемпотентности терялись бы, и обрыв связи создавал бы дубль заметки;
- токены подтверждения терялись бы, и «Выполнить» для умного дома не
  срабатывало бы никогда;
- история разговора терялась бы, и «Ещё вопрос» каждый раз начинал бы заново.

Поэтому всё это вынесено за один узкий интерфейс в `server/src/store.mjs`, а
место хранения выбирается при запуске:

- **файловое** — заметки в `server/data/notes.json`, короткие ключи в памяти.
  Режим по умолчанию, поведение ровно прежнее: локальный запуск, домашний
  компьютер, VPS.
- **KV** — и заметки, и короткие ключи в Deno KV, переживают смену экземпляра.

Оба хранилища проверяются одним набором тестов: шлюз не должен вести себя
по-разному в зависимости от того, где запущен.

Ограничение частоты запросов сознательно оставлено в памяти. На нескольких
экземплярах оно станет приблизительным, но это защита от перегрузки, а не от
потери данных, и ради неё городить общий счётчик не стоит.

Маршрутизация не переписывалась. Между «веб»-моделью HTTP (Request на вход,
Response на выход) и нашей стоит переходник `server/src/fetch-adapter.mjs` —
он притворяется парой req/res. Проверяется он обычными тестами на Node, где
Request и Response настоящие, так что доказывает не себя, а то, что шлюз в
этой модели отвечает так же.

## Почему перед шлюзом стоит прокси

TLS-стек Xiaomi Watch S5 не понимает сертификаты на эллиптических кривых.
Проверено на устройстве пробой из экрана диагностики:

| Адрес | Сертификат | Часы |
| --- | --- | --- |
| api.telegram.org | RSA 2048 | 200 |
| google.com | ECDSA | ошибка 35 |
| cloudflare.com | ECDSA | ошибка 35 |
| letsencrypt.org | ECDSA | ошибка 35 |
| наш адрес на Deno | ECDSA | ошибка 35 |

Код 35 — отказ TLS-соединения, а не ответ сервера: запрос обрывается до
того, как шлюз о нём узнает. Именно поэтому не работало вообще ничего —
и связь, и озвучка.

Сертификат Deno сменить нельзя, а `*.vercel.app` отдаёт RSA. Поэтому
часы обращаются к прокси на Vercel (`api/index.js`), а он пересылает
запросы на шлюз как есть — ни тело, ни заголовки не разбирая, иначе
пострадали бы запись и WAV озвучки.

Вся логика остаётся на Deno: прокси можно убрать в любой момент, если
появится хост с RSA-сертификатом.

## Как обновляется шлюз

Приложение в Deno Deploy подключено к репозиторию на GitHub. Любой push в
`main` собирается и выкладывается автоматически, адрес не меняется:

    https://timew.deprav1.deno.net

Ничего запускать руками не нужно — ни deployctl, ни deno deploy.

Почему именно так: локальная выкладка (`deno deploy`) в этой версии падает
на шаге сборки, а создание приложения проходит. Из-за этого каждое
обновление сервера требовало нового приложения и нового адреса, а значит и
пересборки часов. Сборка из GitHub снимает это целиком.

Что остаётся ручным при создании приложения с нуля: подключить базу
(`database assign timew-kv`) и залить переменные (`env load server/.env`).

## Развёртывание вручную (если нужно с нуля)

Выкладка делается из **вашего** терминала: инструмент хранит токен доступа в
системном хранилище ключей и запрашивает авторизацию интерактивно, через
браузер. Автоматизировать это со стороны нельзя — и не нужно, это три
команды один раз.

Понадобится Deno. Если его нет:

```powershell
winget install DenoLand.Deno
```

Дальше из корня репозитория:

```bash
deno deploy create --app timew-gateway --entrypoint server/src/deno-entry.mjs
```

Откроется браузер с авторизацией — приложение создаётся в вашем аккаунте.

```bash
deno deploy env load server/.env
```

Переменные окружения (`DEVICE_TOKEN`, ключи AI) уезжают из вашего `.env`
сразу все; те, что похожи на секреты, помечаются секретами автоматически.

```bash
deno deploy --prod
```

Команда напечатает адрес вида `https://timew-gateway.deno.net`.

**База.** KV на новой платформе заводится на приложение: в панели
организации → **Databases** → **Add Database** → движок **Deno KV**. В коде
менять ничего не нужно, `Deno.openKv()` подключится к ней сам.

Проверка после выкладки:

```bash
npm run smoke -- https://ваш-адрес
```

Токен подставится из локального `server/.env`, он тот же самый.

Запустить шлюз под Deno локально, ничего не выкладывая:

```bash
npm run deno
```

Полезно, чтобы отделить проблемы кода от проблем хоста.

### Про deployctl

В интернете и в старых инструкциях встречается `deployctl` — это инструмент
предыдущего поколения Deno Deploy (Deploy Classic, выключается в июле 2026).
С новой панелью, где есть разделы Apps, Sandboxes и Databases, он не
работает: запрос на авторизацию просто не подхватывается. Нужен встроенный
`deno deploy`.

Затем нацелить часы на новый адрес и пересобрать:

```bash
npm run setup -- --localhost --url https://ваш-проект.deno.dev
npm run build
```

`--localhost` здесь потому, что домашний шлюз больше не нужен снаружи: часы
ходят в облако.

## Про безопасность

Публичный адрес означает, что шлюз доступен из интернета. Защищает
`DEVICE_TOKEN`: без него любой защищённый эндпоинт отвечает `401`, сравнение
токена устойчиво ко времени, плюс работает ограничение частоты запросов.
Открытым остаётся только `/health`, и он не отдаёт ничего, кроме режима и
версии.

Точка входа для Deno отказывается подниматься без токена: лучше не
запуститься совсем, чем оказаться в интернете открытым.

Ключ AI хранится в переменных проекта и в `.rpk` не попадает.

## Что проверено, а что нет

Проверено на Node: оба хранилища на одинаковом наборе сценариев, переходник
на настоящих Request/Response, и весь шлюз целиком — 101 тест.

Под самим Deno с настоящим KV ранее был выполнен отдельный smoke-прогон.
После текущих изменений его нужно повторить перед новым облачным релизом;
локальный Node-набор уже подтверждён (101 тест), а число smoke-проверок
изменилось вместе с контрактом CORS и статусом сборки.

Не проверена только выкладка на сам хост: она требует аккаунта Deno, а его
создание — единственное, что нельзя сделать за владельца. Команда `npm run
deploy` доведена до шага авторизации и на нём останавливается.
