# Особенности Vela, проверенные на эмуляторе

Всё ниже выяснено запуском приложения в эмуляторе AIoT (образ `vela-miwear-watch-5.0`), а не вычитано в документации. Сборка и проверка синтаксиса эти вещи **не ловят** — приложение компилируется и молча ведёт себя не так.

## Запуск без часов

Эмулятор входит в состав `aiot-toolkit`, который уже стоит в `watch/node_modules`.

```bash
cd watch
npx aiot initEmulatorEnv   # один раз: скачивает ~745 МБ, разворачивает ~2.1 ГБ в ~/.vela
```

CLI `aiot start` спрашивает параметры интерактивно и в неинтерактивной оболочке падает. Виртуальное устройство проще создать через API пакета: `VvdManager.createVvd({ name, imageType: VELA_MIWEAR_WATCH_5, arch: "arm", imageDir, width: "480", height: "480" })`, затем `startVvd({ vvdName })`. Полученный `emulatorInstance` умеет `pushRpk` / `install` / `startApp`, а `getAgent()` даёт `getScreenshot()` и `sendMouse()`.

Приложение перезапускается через adb (`node_modules/@miwt/adb/bin/win/adb.exe`): `shell am stop <пакет>`, затем `shell am start <пакет>`. Команды `input tap` в этой прошивке **нет**.

## Что подтвердилось работающим

- **Сеть.** Запросы `@system.fetch` из приложения доходят до шлюза на хост-машине. Изнутри эмулятора хост доступен как `10.0.2.2` (стандартная схема QEMU user-mode), `localhost` указывает на саму гостевую систему.
- **Хранилище.** `@system.storage` читается и пишется, настройки переживают перезапуск.
- **Запись звука.** `@system.record` возвращает успех и путь к файлу.
- **Полный голосовой путь.** Запись дошла до шлюза (`POST /api/v1/voice 200`), ответ отобразился на экране вместе с распознанным текстом.

## Какой транспорт работает

`request.upload` **молчит**: ни `success`, ни `fail`. Именно он вешал приложение до появления сторожевых таймеров.

Работает чтение файла и отправка сырых байтов: `file.readArrayBuffer` → `@system.fetch` с бинарным телом. Поэтому в `api.js` этот путь стоит первым, а сработавший способ запоминается в хранилище — иначе каждая голосовая команда начиналась бы с ожидания таймаута молчащего пути. Разница в замерах: **4 секунды против 30+**.

На реальной прошивке всё может оказаться наоборот, поэтому порядок не зашит намертво, а берётся из настроек.

## Четыре ловушки, каждая стоила отдельного прогона

**1. Статический `<list-item>` без `for` не рендерится.** Экран оставался пустым: видна была только верхняя панель. Использовать `<list>` можно лишь там, где есть `for`; остальную разметку строить обычными `<div>`.

**2. Составные CSS-селекторы не поддерживаются.** Правило `.talk-button.busy { … }` применялось ко **всем** `.talk-button`, поэтому кнопки всегда выглядели заблокированными. Нужны отдельные самостоятельные классы (`.talk-button` и `.talk-busy`), а класс биндить целиком — `class="{{talkClass}}"`, а не склейкой `class="talk-button {{busyClass}}"`.

**3. `<div>` по умолчанию раскладывает детей в строку.** Без явного `flex-direction: column` заголовок и текст вставали рядом, а кнопка записи — в один ряд с мелкими кнопками.

**4. В шрифте нет символа ⚙** (и, вероятно, других символов вне базовых наборов) — рисуется пустой квадрат. Иконки только текстом или картинкой.

## Молчащие модули — главный вывод

`request.upload` при отправке записи **не вызвал ни `success`, ни `fail`**. Приложение осталось в состоянии «думаю…» навсегда, а запасной путь доставки не включился, потому что был завязан на колбэк ошибки.

Отсюда правило для всего кода часов: **любой системный вызов оборачивается сторожевым таймером** (`watch/src/common/guard.js`). Побеждает первый наступивший исход — успех, ошибка или истёкшее время. Фолбэки переключаются в том числе по таймауту, а не только по `fail`.

Для системных диалогов таймаут не годится — человек может думать сколько угодно, — поэтому там ручной размыкатель: тап по статусу возвращает приложение в рабочее состояние.

## Сторож — это не путь завершения

Продолжение того же правила, которое стоило зависания в v43. Сторожевой таймер спасает от молчащего модуля, но он **не заменяет колбэк**. Если код выбрасывает `success`, потому что ждёт результат другим способом, приложение внешне работает, а на деле каждая операция стоит полного таймаута.

Конкретно: `startFramed` в `audio.js` слушал только `onframerecorded` и `complete`, а `success` был пустой заглушкой:

```js
success: function() {},   // ← запись приехала сюда и была выброшена
```

На прошивке, которая объявляет слот `onframerecorded`, но отдаёт запись обычным `success({uri})`, это давало 18 секунд «заканчиваю…», а потом молчаливое **повторное** включение микрофона. Сторож отработал ровно как задумано — и именно поэтому дефект не выглядел как поломка.

Правило: **все исходы вызова ведут в одну функцию завершения**, и ни один из них не выбрасывает полученные данные. Побеждает первый; остальные становятся no-op. Сторож — последний из исходов, а не единственный.

## Объявленный метод ≠ работающий метод

`"onframerecorded" in record` возвращает `true`, как только слот объявлен, — независимо от того, заполняет ли его прошивка хоть раз. Проверка через `in`, `typeof` и `hasOwnProperty` годится только как **предусловие**: она отсеивает прошивки, где метода нет вовсе, и ничего не говорит о тех, где он есть формально.

Возможность считается подтверждённой только после наблюдаемого результата: пришёл кадр, вернулся байт, сработал колбэк. До этого — запасной путь наготове. В проекте так уже сделано с транспортом записи (`rememberTransferMode`), и теперь так же с кадрами: первая запись без единого кадра выставляет `framedUnsupported`, и остаток сессии приложение идёт файловым путём без повторного крюка.

## Каких методов на самом деле нет

Проверено прямым опросом рантайма (временный зонд выводил `typeof mod.method` на экран — `console.log` до logcat не доходит):

```
prompt:  -show  +showToast  +showDialog  -showContextMenu
request: -upload  +download  +onDownloadComplete
network: getType, subscribe, unsubscribe, uninit
```

Два вывода, каждый ломал функциональность:

**`prompt.show` не существует.** Метода ввода текста в API нет вообще. Мы его придумали, и поэтому кнопки «Спросить»/«Заметка» молча вешали приложение: вызов несуществующей функции бросает исключение, состояние занятости не снималось. Подтверждение косвенное, но убедительное: в разобранных приложениях из образа (QQ, Ximalaya) нет ни одного обращения к вводу текста и ни одного элемента `<input>` — только `showToast` (77 вызовов) и `showDialog`.

Следствие для продукта: **текст на часах ввести нельзя**. Вопросы и заметки надиктовываются голосом, а кнопка «Заметка» передаёт шлюзу `intent=note`, чтобы не проговаривать каждый раз «запиши». Адрес шлюза и токен задаются в `config.js` перед сборкой — экран настроек их только показывает.

**`request.upload` не существует.** Он не «молчал» — его нет. Поэтому единственный рабочий способ отправить запись: `file.readArrayBuffer` → `@system.fetch` с бинарным телом. Вызов оставлен под проверкой `typeof`, на случай прошивки, где метод появится.

`request.download` и `onDownloadComplete` есть — путь озвучки жизнеспособен.

## Чему учат готовые приложения из образа

В `/quickapp/` внутри эмулятора лежат реальные `.rpk`: Xiaomi Smart Home, QQ, Ximalaya, Baidu Map, Kugou. Распаковываются как обычный zip (`adb pull`, затем `unzip`); часть поставляется с читаемым JS, часть — в байткоде `.jsc`.

- **Умный дом Xiaomi не управляет устройствами напрямую.** Он объявляет `system.internal.messagecenter`, то есть работает через телефон. Это независимое подтверждение того, что управлять домом прямо с часов нельзя — и что обход через облако Tuya был верным решением.
- **Оба сторонних приложения объявляют `system.network`** и перед работой спрашивают `getType()`, считая `"none"` отсутствием сети. Мы переняли это: теперь «нет сети на часах» и «шлюз не отвечает» — разные сообщения.
- **В фоне объявляют `system.audio` и `system.request`** — иначе воспроизведение и сетевые операции обрываются при гашении экрана.
- **QQ использует `designWidth: 480`** — подтверждает, что для S5 это правильное значение (Ximalaya рассчитана на 466).
- **Рантайм поддерживает современный JS.** В бандле Ximalaya есть `async`, стрелочные функции и `const`. Ограничение ES5.1 в этом проекте — перестраховка из исходной заготовки, а не требование платформы. Переписывать работающий код смысла нет, но новый писать можно свободнее.

## Ввод: касания вместо мыши, и грубая сетка

`sendMouse` из обёртки **не работает** — события не доходят до рантайма. Работает `sendTouch`, но обёртка его не предоставляет; вызывать надо напрямую через `agent.client.sendTouch({ touches: [{ x, y, identifier: 0, pressure, touch_major: 10 }], display: 0 }, meta, cb)`, где `meta` — `agent.authMate`.

**Координаты нужно пересчитывать.** Рантайм домножает присланное значение на 32767/480 ≈ 68.26: отправленный `x: 287` превращается в `19591`, и LVGL отбрасывает его как выходящий за экран. Поэтому отправлять надо `пиксель × 480 / 32767`.

Следствие: адресуется только сетка с шагом ~68 пикселей. Крупные цели (кнопка «Нажми и говори») нажимаются надёжно, мелкие (надписи в верхней панели) — нет.

**Обязательно снимать касание.** Если не отправить событие с `pressure: 0`, точка остаётся зажатой, рантайм зацикливается на её обработке и весь ввод перестаёт отвечать до перезапуска эмулятора.

Перед прогоном сценария приложение надо гарантированно поднять: `am stop` → пауза → `am start`. Эвристика «кадр легче циферблата» обманывает — системные экраны тоже лёгкие.

## Чего проверить не удалось

- **`prompt.show` не подтверждён.** На нём держатся «Спросить», «Заметка» и подтверждение удаления, но кнопки мелкие и в сетку касаний не попадают.
- **Экран настроек и экран полного ответа** визуально не проверены по той же причине.
- **Озвучка** (`@system.audio` + `request.download`) не проверялась: нужен настроенный синтез на шлюзе.
- **Реальное распознавание речи.** В эмуляторе микрофон не даёт звука, запись получается нулевой длины — приложение показывает «Ничего не записалось». Это ожидаемо и проверяется только на устройстве.
